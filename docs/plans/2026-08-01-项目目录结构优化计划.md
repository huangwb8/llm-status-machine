# 项目目录结构优化实施计划

## 问题是什么

- **当前现象：** 已完成 Python CLI 迁移的源码、测试和文档已经有清晰基础，但仓库根目录仍并列存在旧 Node/Web 栈遗留目录、旧运行数据、未归类图片和过期计划。读者无法仅凭目录名称判断哪些是正在维护的代码、哪些只是迁移证据或可安全再生成的本地文件。
- **影响：** 新贡献者容易把 `data/` 误认为当前数据根，把旧 Web 计划当作可执行方案，也难以判断 `server/`、`public/`、`deploy/` 与 `tools/` 是否仍有作用；这会放大误改、误删历史数据和文档链接失效的风险。
- **已知原因：** Python CLI 迁移保留了旧数据和计划以支持核验，但尚未完成第二步“归档与入口收束”。当前 Python 包本身按领域划分已足够清楚，不是本次混乱的主要来源。

## 要达到什么目标

- **完成后的变化：** 根目录保留既有项目入口、`Prompts.md`、构建配置、位于 `src/` 的功能性源代码，以及 `tests/`、`examples/`、`docs/` 三类辅助内容。`examples/` 只存放独立测试项目和实验 fixture，不承担本项目功能实现。可再生成的本地状态仍留在被忽略的目录；旧 Node/Web 证据有明确归档位置且不会被误作当前实现。
- **不在本次处理范围：** 不重写 Python 领域模块，不改变 RawBundle 格式、CLI 公开命令或实验执行语义；不删除任何 legacy 数据、容器或 volume，也不把运行数据纳入 Git。`Prompts.md` 以及 `init-project` 设定的系统文档 `AGENTS.md`、`CLAUDE.md`、`README.md`、`CHANGELOG.md`、`.gitignore`、`docs/contribution.bac` 均为保护对象，本计划不修改、重命名、移动或删除这些文件。

## 改进方向

### 以“活跃代码、测试项目、文档、可再生成状态、历史证据”划分目录

目录名称应说明内容的生命周期，而不是它曾经使用的技术。保留现有 `src` layout 和领域包：`domain`、`study`、`harnesses`、`execution`、`recording`、`storage`、`evaluation`、`workspaces`、`prompts` 与 `legacy` 已与产品概念一一对应；当前规模下继续拆分只会增加跳转成本。

完成后采用下列目标结构。其中 `var/` 与 `.lsm/` 都是本地、被忽略的状态，不是可提交的项目资产；`var/` 仅在需要暂存旧 Node 数据时创建。

```text
.
├── src/llm_status_machine/       # 当前 Python CLI 与领域实现
├── tests/                        # Python 自动化测试
├── examples/                     # 独立测试项目与实验 fixture，不是产品源码
│   └── agent-workspaces/         # 供 Harness 测试使用的最小工作区
├── docs/
│   ├── adr/                      # 已采纳的架构决策
│   ├── architecture/             # 当前及未来架构说明
│   ├── migration/                # Node/Web → Python 的迁移与核验材料
│   ├── history/                  # 已失效但需保留的需求背景
│   └── plans/
│       └── archive/node-web/     # 已不适用于 Python CLI 的历史计划
├── tmp/                          # 可随时清理的 smoke、手工验证和截图产物
├── .lsm/                         # 默认实验数据根（忽略）
├── var/legacy-node/              # 可选的旧 file-store 本地暂存（忽略）
├── pyproject.toml / uv.lock / Makefile
├── Prompts.md                    # 原始开发诉求，保留原路径与内容
├── README.md / CHANGELOG.md / AGENTS.md / CLAUDE.md
└── .gitignore                    # init-project 系统文档均保持不变
```

这让用户在根目录只需看见“如何构建、代码在哪里、如何验证、说明在哪里”；实验结果与迁移原件则不会伪装成源码。

### 将旧 Node/Web 内容归档，而不是与活跃文档混放

迁移指南和盘点报告仍有实际用途，应移动到 `docs/migration/` 并继续保留其校验摘要。过期的 Node/Web 实施计划则移动到 `docs/plans/archive/node-web/`，并在归档目录放一页简短说明，明确它们只用于追溯历史决定，不能指导当前 Python CLI 开发。

`Prompts.md` 虽然记录原始开发诉求，不是产品中的 Prompt revision，但它是受保护的项目入口文件，必须保留在仓库根目录，不得改名、移动、删除或改写。`init-project` 设定的系统文档同样不纳入本次目录优化。`docs/hosted-control-local-runner-architecture.md` 是未来方向，应移至 `docs/architecture/`，而不是归档；移动时只更新非保护文件中的必要内部链接。

### 显式隔离旧数据与一次性遗留物

当前 `data/` 是旧 Node file store，不是 Python CLI 默认数据根；而命令行 `legacy` 子命令仍默认为该相对路径，容易形成错误的隐式依赖。迁移时改为要求用户显式传入 legacy 数据源路径；如需把本机旧数据继续放在仓库旁，统一使用 `var/legacy-node/` 并由 `.gitignore` 排除。移动前后运行 inventory/validate 并对照既有 checksum，确认文件数与摘要一致；不符合时停止移动并使用原目录继续只读导入。

已确认没有已跟踪引用的 `image/AGENTS/1779724061392.png` 不属于当前文档资产，可在确认 Git 历史足以保留追溯后删除。只含 `.DS_Store` 或为空的 `server/`、`public/`、`deploy/`、`tools/` 以及失效的根目录工作区文件同样移除；`dist/`、虚拟环境、测试缓存和 `tmp/` 继续作为可再生成内容处理，不迁入源码目录。

### 明确测试项目与临时工作区的边界

`examples/` 只用于存放可独立运行或供 Harness 操作的测试项目、实验工作区与 fixture；其中可以包含被测代码，但不得承载 `llm-status-machine` 的功能性源代码，也不得成为产品运行时依赖。项目功能实现统一位于 `src/llm_status_machine/`。把 `examples/buggy-js/` 移至 `examples/agent-workspaces/buggy-js/`，以表明它是供 agent 修复的测试工作区，而非本项目的遗留 JavaScript 应用。`tmp/` 仍是唯一的项目内临时根：README quickstart、`make smoke` 和前端截图规则继续使用其子目录，避免把验证产物散落到 `examples/` 或仓库根目录。

## 实施范围与顺序

1. 建立迁移清单：对 tracked、untracked 和 ignored 顶层内容逐项标注“活跃、可再生成、历史证据或待删除”，并对旧 `data/` 记录移动前的 inventory、文件数与摘要；先确认没有外部脚本依赖待删除目录。
2. 先执行纯文档和测试项目的 Git move：整理 `docs/` 分类、归档 Node/Web 计划与 agent workspace fixture，并在同一变更中修复非保护文件中的仓库内链接；明确排除 `Prompts.md` 和 `init-project` 系统文档。
3. 收束运行数据边界：将本地旧 file store 安全移至 `var/legacy-node/`（或保留在用户指定的仓库外路径），移除 `data/states/.gitkeep`，更新迁移文档和 legacy CLI 的显式路径约定；不要迁移或改写原始数据内容，也不修改 `.gitignore`。
4. 删除已确认无消费者的 Node/Web 空目录、未引用图片与无配置内容的 workspace 文件；不得把 `Prompts.md` 或 `init-project` 系统文档纳入删除、迁移或内容调整范围。

## 如何确认完成

- 根目录不再包含 `data/`、`image/`、`server/`、`public/`、`deploy/`、`tools/` 或空的 `llm-status-machine.code-workspace`；`Prompts.md` 仍以原名称保留在根目录，活跃目录与本计划的目标树一致。
- `src/llm_status_machine/` 是唯一的项目功能性源码目录；`examples/` 中的内容仅作为独立测试项目或实验 fixture，产品代码不从该目录导入实现。
- `rg` 检查不再发现非保护文件指向已迁移旧路径的链接；所有被调整文档的链接可从仓库根目录正确解析。
- 对 legacy 原件运行 `lsm legacy inventory` 和 `lsm legacy validate`，并与移动前盘点的计数、SHA-256 摘要一致；随后执行一次只读 `lsm legacy import` 到全新的 `.lsm/` 数据根并验证 seal。
- 运行 `uv run pytest`、`uv build` 和 `make smoke`；核心 smoke 必须以 Simulator、`concurrency=1`、`state_policy=carry_forward` 连续完成 3 个 episode，并保留 stdout/stderr、workspace snapshot、Git diff 与 seal。
- `git diff --check` 无格式错误；执行前后对照确认 `Prompts.md` 与 `init-project` 系统文档的路径和内容均未变化。

## 风险与待确认事项

- 旧 `data/` 当前含未提交但有核验价值的历史运行原件；任何移动前必须保存新的只读 inventory 和 checksum。Git 并不保存这些被忽略原件，不能把“目录清理”误当作可逆的 Git 操作。
- 历史计划中包含对已删除 Node/Web 文件的引用。它们应作为归档材料保留原文，不应为了消除全部旧路径而改写历史；只需在归档说明中标示其失效范围。
- `Prompts.md` 和 `init-project` 系统文档可能被仓库外工具依赖，因此将其作为目录优化的硬边界；若其他步骤意外产生这些文件的 diff，应停止交付并撤销对应改动。
